# Основные блоки декомпозиции

Источник — задача **«(ХХХ) Шаблон. Декомпозиция фичи со стороны QA»** в Asana (`1205699014619431`, проекты `FD: Templates` и `Disco Team QA`). Ниже — блоки, относящиеся к декомпозиции ТЗ. Нумерация шаблонная, поэтому в списке есть пропуски. Сверить дословную формулировку или посмотреть блок, которого здесь нет, можно через MCP: `asana_get_task` + `asana_get_subtasks` по этому GID.

**Чего в декомпозиции нет** (есть в шаблоне, из состава исключено):

- задачи на просмотры («Прогон билда перед просмотром-1…4»);
- задача «Чек-лист на регрессию в Qase и ТК на автоматизацию»;
- вложенные подзадачи «Написание чек-листа»;
- вложенная подзадача «Проверка реакции события при удалении лаунчера».

Единственные вложенные подзадачи, которые заводятся, — платформы внутри блока 14.

**Заголовок блока один и тот же у всех фич, описание проверок — своё.** Наполнять конкретикой из ТЗ, а не копировать формулировки шаблона.

## Как пользоваться списком

1. Пройти **все** блоки ниже сверху вниз. Ни один не пропускать молча.
2. Обязательные — включить всегда, наполнив спецификой фичи.
3. Условные — включить, если условие выполняется.
4. Если по ТЗ блока быть не может (нет туториалов, нет покупок, событие не серверное) — **не выбрасывать молча**. Собрать такие блоки в отдельный список и задать вопрос в ответе до отдачи файла на ревью. Формат — в конце этого файла.
5. Если раздела в ТЗ нет, но блок обязательный — оставить блок пустым и сказать об этом на ревью. Проверки не придумывать.
6. Префикс `ХХ.` заменить на код фичи: `IDL.`, `CAH.`.

## Планирование

### 1. Создание тест-плана — обязательный

```
На этапе планирования выделить ключевые точки и даты на задачи для входа в тестирование.
- Выбрать из шаблона декомпозиции необходимые проверки и добавить их в секцию QA проекта фичи
- Добавить специфичные проверки фичи
- Проставить поле <проект>: Проверка в QA
- Проставить зависимости от компонентов в разработке
- Проставить QA-сложность/QA Estimate
- Определить ключевые и наиболее багоопасные задачи из декомпозиции
- Определить конечные ДД отталкиваясь от дат выпуска фичи/регрессии на основании QA Estimate
```

### 2. Запросить читы для тестового окружения — обязательный

Исходная формулировка шаблона: «Необходимо на основе ТЗ проанализировать, какие читы будут необходимы для комфортного тестирования. Отдельно подумать над необходимостью читов на проде.»

**Свои читы не выдумывать.** Перечислить основное, что понадобится при разработке фичи:

- выдача валют и токенов фичи;
- перемотка времени (сдвиг даты, ускорение таймеров);
- набор прогресса (установка уровня, этапа, счётчиков);
- принудительный старт и завершение события;
- сброс просмотренных туториалов и флагов «видел фичу».

Из этого списка брать то, что применимо к фиче по ТЗ, и добавлять только очевидное из её механики. Мелкие точечные читы под каждый параметр не расписывать.

## Запуск и инфраструктура

### 3. Проверка запуска события — обязательный

«Проверить старт события при различных условиях, в том числе на сохранении для проверки релиза.»

Наполнить условиями запуска из ТЗ: порог уровня, расписание, ограничения по остатку времени, первый и повторный запуск, приоритеты промо-окон.

### 4. Проверка лаунчера события — обязательный

```
Проверить:
- Уровень запуска
- Фичефлаг (если есть)
- Даты запуска и завершения
- Зависимость от паков
```

Наполнить из ТЗ: конкретный порог уровня и признак «настраиваемый параметр», имя фичефлага и поведение при его выключении, расписание и длительность события, состав паков, без которых событие не стартует.

Пункт про фичефлаг включать, только если фичефлаг у фичи есть. Пункт про зависимость от паков остаётся всегда: если своего пака у фичи нет, это тоже проверка — событие стартует без ожидания загрузки.

Вложенных подзадач у блока не заводить.

### 5. Проверка паков события — условный: у фичи есть свой пак ресурсов

```
Проверить:
- Паки скачиваются с заданного уровня
- Паки скачиваются при заниженной скорости интернета
- Событие не стартует без скачанных паков
- Паки скачиваются при включении интернета
- Не появляется окно дозагрузки ресурсов при старте скачивания паков
- Событие стартует при дозагрузке паков (если другие условия для запуска выполнены)
```

Дополнить составом пака из ТЗ: сколько локаций, биомов, вариантов оформления в него входит.

### 6. Проверка завершения события — обязательный

«Проверить завершение события при различных условиях, а также начисление и выдачу наград в различных условиях.»

**Завершение по прогрессу и завершение по таймеру — всегда разные блоки.** Если в ТЗ упомянуты оба условия завершения, это два блока, без исключений: `ХХ. Проверка флоу завершения по прогрессу` и `ХХ. Проверка флоу завершения по таймеру`. Совмещать их в одном блоке нельзя, даже когда ТЗ описывает их одним общим флоу и различий на первый взгляд мало. Правило про дубли здесь не применяется — общие пункты повторяются в обоих блоках, потому что проверяются они разными прогонами.

Прочие сценарии завершения с отдельным условием входа (бонусный этап, вытеснение следующим событием) выносить в свои блоки по тому же принципу.

### 10. Проверка работы без интернета — обязательный

В шаблоне описание пустое. Наполнить: запуск с ранее скачанным паком и последними загруженными настройками, поведение при обрыве связи посреди флоу, выдача наград и доход аналитики после восстановления сети.

## Данные, сервер, сохранки

### 12. Проверка синхронизации и обновления — обязательный

```
Проверить ситуации:
- Прогресс по событию сохраняется при синхронизации устройств
- Прогресс события сохраняется при переустановке приложения
- Прогресс события сохраняется после обновления игры
- Таймер события работает без прерывания и остановок
- Синхронизация во время активных туториалов
- Обновление и довыдача наград после обновления и синхронизации при различном прогрессе
Синхронизацию проверить по google, facebook, appleid, game center, google play games.
```

Дополнить перечнем того, что в этой фиче должно переживать синхронизацию: счётчики, прогресс, накопления, состояния особых режимов.

### Проверка графики и визуала фичи — обязательный

Блока с таким названием в шаблоне Asana нет, он введён по договорённости: **весь визуал фичи проверяется одной задачей.**

Собрать сюда: арт и анимации объектов, иконку и её состояния, вёрстку всех окон, VFX, соответствие финальным макетам. Внутри — короткий список областей, а не задача на каждое окно и пункт на каждую подпись.

Отдельный блок окно получает только при наличии **своей механики** (расчёты, состояния, ветвления, работа с сервером).

## Если блок не применим

Не удалять молча. Собрать все спорные блоки и задать вопрос **в ответе** (не в файле) до отдачи файла на ревью, одним списком:

```
По ТЗ не могу решить сам — подтвердите, убирать эти разделы или наполнять:

- Проверка туториалов — в ТЗ раздела про обучение нет. Туториалы точно не планируются?
- Проверка покупок на Inapp-билде — в ТЗ нет ни одной точки покупки за реальные деньги. Верно?
- Проверка нотификаций — в ТЗ пушей нет. Их не будет или раздел ТЗ ещё не написан?

Про серверное взаимодействие в ТЗ ясности нет — какие из этих блоков нужны?
- Проверка отправки запросов на сервер / клиент-серверное взаимодействие — событие серверное или полностью клиентское?
- Проверка подхвата изменений с сервера — фича читает настройки с сервера на живом клиенте?
- Проверка работы на Prod-сервере — в шаблоне помечена как актуальная только для серверных событий.
```

Чего в этом списке быть не должно: **вопросов про версию.** Целевую версию задач QA проставляет сам.
