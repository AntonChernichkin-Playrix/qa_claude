# Обязательные разделы декомпозиции

Источник — задача **«(ХХХ) Шаблон. Декомпозиция фичи со стороны QA»** в Asana (`1205699014619431`, проекты `FD: Templates` и `Disco Team QA`). В шаблоне 38 блоков, ниже — 25 из них: те, что относятся к декомпозиции ТЗ. Нумерация оставлена шаблонная, поэтому в списке есть пропуски. Если понадобится сверить дословную формулировку или посмотреть блок, которого здесь нет, задача открывается через MCP: `asana_get_task` + `asana_get_subtasks` по этому GID.

**Чего в декомпозиции больше нет** (было в шаблоне, из состава исключено):

- задачи на просмотры («Прогон билда перед просмотром-1…4»);
- задача «Чек-лист на регрессию в Qase и ТК на автоматизацию»;
- вложенные подзадачи «Написание чек-листа» — не создавать ни в файле, ни в Asana;
- вложенная подзадача «Проверка реакции события при удалении лаунчера».

Единственные вложенные подзадачи, которые заводятся, — платформы внутри блока 14.

Эти разделы встречаются в каждой фиче. **Заголовок один и тот же, описание проверок — своё под каждую фичу.** Задача декомпозиции не в том, чтобы скопировать блок, а в том, чтобы наполнить его конкретикой из ТЗ.

## Как пользоваться списком

1. Пройти **все** блоки ниже сверху вниз. Ни один не пропускать молча.
2. Обязательные — включить всегда, наполнив спецификой фичи.
3. Условные — включить, если условие выполняется. Если по ТЗ непонятно, выполняется ли, — **это вопрос на уточнение, а не повод удалить блок**.
4. Если анализ ТЗ говорит, что блока быть не может (нет туториалов, нет покупок, событие не серверное) — **не выбрасывать молча**. Собрать такие блоки в отдельный список и задать вопрос до того, как отдавать файл на ревью. Формат вопроса — в конце этого файла.
5. Префикс `ХХ.` в шаблоне заменить на код фичи: `IDL.`, `CAH.`. Блок 38 идёт с префиксом `ХХ+1.` — так в шаблоне помечена задача следующей итерации.

## Планирование

### 1. Создание тест-плана — обязательный

```
На этапе планирования выделить ключевые точки и даты на задачи для входа в тестирование.
- Выбрать из шаблона декомпозиции необходимые проверки и добавить их в секцию QA проекта фичи
- Добавить специфичные проверки фичи
- Проставить поле <проект>: Проверка в QA
- Проставить зависимости от компонентов в разработке
- Проставить QA-сложность/QA Estimate
- Определить ключевые и наиболее багоопасные задачи из декомпозиции
- Определить конечные ДД отталкиваясь от дат выпуска фичи/регрессии на основании QA Estimate
```

Дополнить строкой с ключевыми точками готовности компонентов этой фичи.

### 2. Запросить читы для тестового окружения — обязательный

Исходная формулировка шаблона: «Необходимо на основе ТЗ проанализировать, какие читы будут необходимы для комфортного тестирования. Отдельно подумать над необходимостью читов на проде.»

**Здесь общей формулировки недостаточно — нужен список.** Вывести его из механики: всё, что игрок получает долго или случайно, должно выдаваться читом. Типовые категории: установка уровня/прогресса, сдвиг времени и принудительный старт/финиш, выдача каждой валюты фичи, спавн сущностей нужного грейда, телепорт по этапам и скип этапа, сброс просмотренных туториалов, сброс флага «видел фичу ранее», управление очередью промо-окон, переключение сложности.

## Запуск и инфраструктура

### 3. Проверка запуска события — обязательный

«Проверить старт события при различных условиях, в том числе на сохранении для проверки релиза.»

Наполнить условиями запуска из ТЗ: порог уровня, расписание, ограничения по остатку времени, первый и повторный запуск, приоритеты промо-окон.

### 4. Проверка лаунчера события — условный: есть лаунчер

```
Проверить:
- Даты и время события в игре соответствуют указанным в настройках конфига
- Лаунчер отрабатывает при выключенном кондишене "false"
- Завершение лаунчера через <finish> и <false/>
- Изменение дат события
```

Отдельная пометка шаблона: «Для GFF нет данных для проверки, необходимо расписать условия».

Вложенных подзадач у блока не заводить: «Проверка реакции события при удалении лаунчера» из состава исключена.

### 5. Проверка паков события — условный: у фичи есть свой пак ресурсов

```
Проверить:
- Паки скачиваются с заданного уровня
- Паки скачиваются при заниженной скорости интернета
- Событие не стартует без скачанных паков
- Паки скачиваются при включении интернета
- Не появляется окно дозагрузки ресурсов при старте скачивания паков
- Событие стартует при дозагрузке паков (если другие условия для запуска выполнены)
```

Дополнить составом пака: сколько локаций, биомов, вариантов оформления должно в него войти.

Про режим монтирования (OnDemand или автозагрузка) в блок ничего не писать — этот пункт из проверки паков исключён.

### 6. Проверка завершения события — обязательный

«Проверить завершение события при различных условиях, а также начисление и выдачу наград в различных условиях.»

Если в ТЗ несколько сценариев завершения с разными условиями входа — **разбить на отдельные блоки** (по прогрессу, по таймеру, бонусный этап). Так сделано в эталонной декомпозиции IDL.

### 10. Проверка работы без интернета — обязательный

В шаблоне описание пустое. Наполнить: запуск с ранее скачанным паком и последними загруженными настройками, поведение при обрыве связи посреди флоу, выдача наград и доход аналитики после восстановления сети.

## Кросс-функциональные

### 9. Проверка аналитики — обязательный

**Перечень событий не придумывать.** Состав аналитики описывает аналитик; сочинённый список всё равно пойдёт в переписывание. В блоке — только ссылки:

- Общая таблица событий аналитики: `https://docs.google.com/spreadsheets/d/1ZhQCuEzx1d1Sj8lbCiJ5lBX5GUqOvpdiHrX3BsVeYRc/edit#gid=0`
- Есть явная ссылка на таблицу аналитики по фиче или на задачу аналитиков — приложить её, и на этом всё.
- Ссылки нет или она неявная (в ТЗ «Заполняется аналитиком», ссылка на общий документ без раздела по фиче) — **оставить блок пустым** и поставить `[GAP-xx]`: раздел аналитики не получен, задача заблокирована.

Плюс из шаблона, это писать можно: «Проверить работу фичи без интернета, в том числе выдачу наград и приход аналитики после подключения к сети.»

### Проверка графики и визуала фичи — обязательный

Блока с таким названием в шаблоне Asana нет, он введён по договорённости: **весь визуал фичи проверяется одной задачей.**

Собрать сюда: арт и анимации объектов, иконку и её состояния, вёрстку всех окон, VFX, соответствие финальным макетам. Внутри — короткий список областей, а не задача на каждое окно и пункт на каждую подпись.

Отдельный блок окно получает только при наличии **своей механики** (расчёты, состояния, ветвления, работа с сервером). Сложный арт сам по себе — не повод выносить окно в отдельную задачу.

## Если блок не применим

Не удалять молча. Собрать все спорные блоки и задать вопрос **до** отдачи файла на ревью, одним списком:

```
По ТЗ не могу решить сам — подтвердите, убирать эти разделы или наполнять:

- Проверка туториалов — в ТЗ раздела про обучение нет. Туториалы точно не планируются?
- Проверка покупок на Inapp-билде — в ТЗ нет ни одной точки покупки за реальные деньги. Верно?
- Проверка нотификаций — в ТЗ пушей нет. Их не будет или раздел ТЗ ещё не написан?

Про серверное взаимодействие в ТЗ ясности нет — какие из этих блоков нужны?
- Проверка отправки запросов на сервер / клиент-серверное взаимодействие — событие серверное или полностью клиентское?
- Проверка подхвата изменений с сервера — фича читает настройки с сервера на живом клиенте?
- Проверка работы на Prod-сервере — в шаблоне помечена как актуальная только для серверных событий.
```

Последняя формулировка важна: **отсутствие раздела в ТЗ и отсутствие функциональности — разные вещи.** Первое чаще означает, что ТЗ недописано, и тогда это `[GAP-xx]`, а не удаление блока.

Чего в этом списке быть не должно: **вопросов про версию.** Целевую версию задач QA проставляет сам, декомпозиция её не касается. Если пометка в ТЗ ограничивает объём функциональности, это `[GAP-xx]` про объём релиза, а не вопрос о номере версии.
