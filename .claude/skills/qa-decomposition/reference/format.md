# Формат блока декомпозиции

Один блок в файле = одна будущая подзадача в Asana. Заголовок блока станет `name`, тело — `notes`.

## Скелет

```markdown
## <N>. <ПРЕФИКС>. Проверка <объекта или флоу>

Требования (ТЗ: <Раздел 1>; <Раздел 2>):
1. <атомарная проверка>
2. <атомарная проверка>
...

<опциональная строка уточнения области или специфики>

Источник: ТЗ «<точное название документа>». [ГД] — значение из таблицы баланса, [GAP-xx] — пробел/противоречие в ТЗ.
```

## Название

`<ПРЕФИКС>. Проверка <чего>`

| Элемент | Правило |
|---|---|
| `<ПРЕФИКС>` | Короткий код фичи заглавными с точкой: `IDL.`, `MQ.`. Ставится в каждой задаче — по нему фильтруют в Asana |
| Глагол | `Проверка <существительное в родительном падеже>` — основная форма. `Проверить <что-то>` — только для разовых точечных задач |
| Уточнение | В скобках в конце: `(доработка)`, `(доработки)` — если блок про изменения относительно предыдущей версии фичи |

**Версию в названии не писать.** Её проставляет QA сам после создания задач. Не подставлять номер версии, не переносить его из ТЗ и не спрашивать, какая версия целевая.

Примеры:

```
IDL. Проверка запуска события
IDL. Проверка шахт с вагонетками
IDL. Проверка флоу завершения по таймеру (доработка)
MQ. Проверка клонов-ботов
```

## Заголовок требований

Первая строка тела указывает, откуда взяты проверки:

| Ситуация | Строка |
|---|---|
| Всё из ТЗ | `Требования (ТЗ: Условия запуска механики; Логика старта события):` |
| Из шаблона + ТЗ | `Требования (шаблон декомпозиции + ТЗ: Работа без интернета):` |
| Только из шаблона | `Требования (шаблон декомпозиции):` |
| Из внешнего документа | `Требования (ТЗ: Уведомления):` + ссылка отдельной строкой |

Разделы ТЗ перечислять **точными названиями** из документа через `;`. По ним ревьюер проверяет, что ничего не потеряно.

## Список проверок

- **Нумерованный** список — для требований из ТЗ. Номера нужны, чтобы на ревью ссылались на конкретный пункт.
- **Маркированный** список — для процессных задач, где это последовательность действий, а не набор требований.
- Одна строка = одна проверка. Без вложенных списков: если хочется вложенности, это два блока или две проверки.
- Формулировка утвердительная — описывает ожидаемое поведение, а не действие тестировщика:
  - Хорошо: `Событие не запускается, если до его конца осталось меньше 24 часов.`
  - Плохо: `Проверить, что будет, если до конца события мало времени.`
- Числа и параметры переносить из ТЗ дословно, с пометкой `(настраиваемый параметр)`, если так сказано в ТЗ.
- Ветки первого и повторного запуска, платного и бесплатного действия и т. п. писать отдельными пунктами с префиксом: `Первый запуск: …`, `Повторный запуск: …`.

## Строка уточнения

После списка — одна-две строки свободного текста, когда нужно:

- **Область охвата:** `Область: кнопки всех окон (стартовое, банк, инфо, дорога наград, переходы, завершения), кнопка пушки, кнопки шахт, зелёная кнопка ворот.`
- **Специфика фичи** в шаблонном блоке: `Специфика IDL: счётчик платных выстрелов, прогресс разрушения камней, накопления вагонеток, состояние Последнего Шанса.`
- **Договорённость:** `ОР согласовать с Lead QA и ОЗФ-программистом.`

## Подвал

Последняя строка каждого блока, выведенного из ТЗ:

```
Источник: ТЗ «IDL. Айдлер ремастер WIP». [ГД] — значение из таблицы баланса, [GAP-xx] — пробел/противоречие в ТЗ.
```

Название документа — точно как в исходнике. Легенду маркеров повторять в каждом блоке: в Asana задачи читают по одной, вне контекста файла.

Процессные задачи (тест-план, читы, мердж в мастер) подвал не несут — они не выводятся из ТЗ.

## Полный пример

```markdown
## 6. IDL. Проверка запуска события

Требования (ТЗ: Условия запуска механики; Логика старта события):
1. Событие доступно после прохождения 26 уровня (настраиваемый параметр).
2. Событие запускается, если игра запущена в даты активности по расписанию (GAM).
3. Событие не запускается, если до его конца осталось меньше 24 часов.
4. Первый запуск: при запуске игры выводится туториал на иконку события согласно GAM.
5. Туториал на иконку запускается в точках: выход из матч-3, разворачивание игры, переход между аквариумами.
6. Первый запуск: событие не запускается, пока игроку не показаны туториал на иконку и окно старта события.
7. Повторный запуск: в HUD аквариума отображается иконка с красным маркером «!».
8. Повторный запуск: бочки за уровни не начисляются, пока игрок не увидит промо-окно и не нажмёт Start.
9. Для первого и повторного запуска — разные приоритеты в GAM.
10. Проверка на сохранках игроков из старого теста IDLERA.

Источник: ТЗ «IDL. Айдлер ремастер WIP». [ГД] — значение из таблицы баланса, [GAP-xx] — пробел/противоречие в ТЗ.
```

Пункт 10 в ТЗ отсутствует — добавлен из QA-опыта. Так и должно быть: ТЗ даёт каркас, тестировщик достраивает.
