# Декомпозиция ТЗ на QA-задачи

Превращает ТЗ фичи в набор задач-проверок: сначала в markdown-файл на ревью, затем — подзадачами в Asana через MCP.

**Главный принцип: ничего не создавать в Asana, пока файл не согласован.** Asana — последний шаг, только после явного «ок» и полученной ссылки.

**Второй принцип: в файле только проверки.** Декомпозиция — это чистый список проверок, выведенных из ТЗ и шаблона. Не пробелы в ТЗ, не анализ, не рассуждения. Чего в ТЗ нет — того в файле нет.

## Порядок работы

Шесть шагов строго последовательно. Не перескакивать вперёд и не совмещать.

### Шаг 0. Показать план

**Первым же ответом, до любых действий**, вывести краткий план:

```
План:
1. Найду и прочитаю ТЗ целиком.
2. Соберу декомпозицию в docs/decomposition-<slug>.md — блоки шаблона + разделы ТЗ.
3. Отдам файл на ревью: состав блоков, покрытие разделов ТЗ. Жду правок.
4. После вашего «ок» попрошу ссылку на родительскую задачу в Asana.
5. Создам подзадачи.

От вас: ревью файла и ссылка на задачу в Asana.
```

Дальше сразу переходить к шагу 1, не дожидаясь ответа на план.

### Шаг 1. Найти ТЗ

Аргумент вызова: `$ARGUMENTS`

**ТЗ всегда лежит внутри проекта.** Искать только в нём — в `~/Downloads`, `~/Desktop` и других папках вне проекта не заглядывать.

1. Если аргумент задан — это путь к файлу ТЗ или его имя. Взять без переспроса; уточнять только если файл не найден или под описание подходит больше одного. Аргумент может быть и просто кодом фичи — тогда искать файл по нему в проекте.
2. Если аргумента нет — искать `*.md` и `*.pdf` в корне проекта и в `docs/`, исключая уже существующие `docs/decomposition-*.md`. Отсортировать по времени изменения, показать кандидатов, подтвердить выбор.
3. Если в проекте подходящего файла нет — сказать об этом и попросить положить ТЗ в проект. Не искать за его пределами и не угадывать.
4. Основной формат — `.md`. Если пришёл PDF, извлечь текст:
   ```bash
   uv venv /tmp/pdfenv -q && uv pip install --python /tmp/pdfenv/bin/python pypdf -q
   /tmp/pdfenv/bin/python -c "
   from pypdf import PdfReader
   r=PdfReader('<путь>')
   open('/tmp/tz.txt','w').write(''.join('\n===== PAGE %d =====\n'%i+(p.extract_text() or '') for i,p in enumerate(r.pages,1)))"
   ```
   В извлечённом тексте маркеры списков (`•`, `◦`, `1.`) уезжают в конец страницы отдельными строками — ориентироваться на смысл, а не на отступы. Таблицы баланса разваливаются: не пытаться восстановить числа, ставить `[ГД]`.
5. **Прочитать ТЗ целиком.** Не по диагонали: половина проверок рождается из фраз «Важно!», «Например», «может меняться», сносок и примечаний.
6. Зафиксировать точное название документа — оно пойдёт в строку `Источник:` каждой задачи.
7. Выписать оглавление ТЗ — список разделов и подразделов. Это скелет декомпозиции и чек-лист покрытия.

### Шаг 2. Собрать декомпозицию в файл

Создать `docs/decomposition-<slug>.md` (slug — короткое имя фичи, например `idl-remaster`).

Порядок сборки:

1. **Взять основные блоки** из [reference/template-blocks.md](reference/template-blocks.md) — это каркас. Заголовки у всех фич одинаковые, **описания проверок — свои**: каждый блок наполнить конкретикой из ТЗ, а не скопировать. Часть блоков помечена как условные — включать только при выполнении условия.
2. **Пройти по оглавлению ТЗ сверху вниз** и добавить функциональные блоки по разделам ТЗ. Они вставляются в середину, между блоком про завершение и кросс-функциональными. Правила укрупнения — в разделе «Как резать ТЗ на блоки» ниже.
3. **Наполнить каждый блок проверками** по формату из [reference/format.md](reference/format.md). Только то, что прямо написано в ТЗ или в шаблоне.
4. **Собрать вопросы по неприменимым обязательным блокам** — см. следующий раздел. Это делается до ревью, вопросы идут в ответ, а не в файл.
5. Свести таблицу покрытия: какой раздел ТЗ в какой блок лёг.

Файл содержит **только текст будущих задач** — то, что уедет в Asana. Никаких рассуждений о процессе, найденных проблемах ТЗ и открытых вопросах внутри блоков.

### Шаг 2а. Уточнить неприменимые обязательные блоки

Если по ТЗ обязательного блока в этой фиче быть не может — нет туториалов, нет покупок, событие не серверное — **не удалять блок молча и не тащить его пустым**. Собрать все такие случаи и задать вопрос одним списком в ответе, до отдачи файла на ревью. Формат вопроса — в конце [reference/template-blocks.md](reference/template-blocks.md).

**Про версию не спрашивать.** Номер версии в названиях задач не пишется — его проставляет QA сам.

### Шаг 3. Попросить ревью

Показать в ответе:
- путь к файлу и число блоков;
- таблицу покрытия: раздел ТЗ → номер блока (и явно — что не покрыто);
- вопросы из шага 2а по неприменимым обязательным блокам;
- спорные решения: что объединил, какие обязательные блоки предлагаешь убрать.

Затем прямо попросить ревью и **остановиться**. Не начинать создавать задачи и не предлагать это делать до правок.

### Шаг 4. Внести правки

Править файл по замечаниям. После правок — короткая сводка: что изменилось. Снова ждать подтверждения. Цикл повторять, пока не скажут, что всё устраивает.

### Шаг 5. Создать подзадачи в Asana

1. Попросить **ссылку на родительскую задачу** в Asana. Не искать её самому и не угадывать проект.
2. Из ссылки вида `https://app.asana.com/1/<workspace>/project/<project_gid>/task/<task_gid>` взять последний `<task_gid>`. В старом формате `/0/<project>/<task>` — тоже последний сегмент.
3. Проверить задачу перед записью: `asana_get_task` — показать название, проект, текущее число подзадач. Подтвердить, что цель верная.
4. Создать подзадачи через `asana_create_subtask` (`parent`, `name`, `notes`).
5. **Asana вставляет новую подзадачу в НАЧАЛО списка, а не в конец.** Поэтому создавать **с конца файла к началу** — тогда итоговый список совпадёт с файлом.
6. Единственные вложенные подзадачи — платформы внутри блока «Проверка фичи на разных платформах». Создавать вторым проходом, с `parent` = gid блока платформ, тоже с конца к началу. Никаких других вложенных подзадач не создавать.
7. Ничего не назначать и не проставлять дедлайны, если об этом не просили.
8. После создания **проверить порядок**: получить список подзадач и сверить с порядком блоков в файле. Если порядок не совпал — переставить через `asana_set_parent_for_task` с `insert_after`, идя по файлу сверху вниз и передавая gid предыдущей подзадачи (для первой — `null`).
9. По завершении — отчёт: сколько создано, ссылка на родителя, подтверждение, что порядок сверен, список неудавшихся (если были) с причиной.

Если MCP-сервер Asana недоступен, не переходить на прямые curl-запросы молча — сказать об этом и предложить вариант.

## Как резать ТЗ на блоки

**Целевой состав: основные блоки шаблона + блоки по заголовкам ТЗ.** Ничего сверх этого не придумывать.

**По умолчанию — один блок на раздел ТЗ.** Блоков должно быть мало: чем меньше, тем лучше читается декомпозиция.

Объединять, когда:
- разделы ТЗ **логически связаны** или проверяются одним прогоном. Пример: стартовое окно, банк, инфо-окно, окна завершения → одна задача «Проверка UI-окон»; список окон перечислить внутри;
- раздел ТЗ **пустой или чисто справочный** («Графика», «Полезные ссылки») — влить в соседний блок или в кросс-функциональные.

Дробить — когда внутри одного раздела ТЗ описаны сценарии с **разными условиями входа**, и в одном блоке они не читаются. Пример: «Логика завершения» → завершение по прогрессу, завершение по таймеру, бонусный этап. В остальных случаях оставлять один блок.

**Завершение по прогрессу и по таймеру — всегда отдельные блоки.** Это правило без исключений: если в ТЗ упомянуты оба условия завершения, заводится два блока. Не объединять их ни при общем флоу в ТЗ, ни при малом числе различий, ни ради сокращения количества блоков. Подробнее — блок 6 в [reference/template-blocks.md](reference/template-blocks.md).

**Проверки не должны дублироваться.** Если требование уже проверяется в другом блоке — не повторять его, а оставить в том блоке, где оно по смыслу основное. Исключение — блоки завершения по прогрессу и по таймеру: общие пункты флоу повторяются в обоих, потому что это два разных прогона.

### Графика и визуал — одна задача

Весь визуал фичи — арт и анимации объектов, иконка и её состояния, вёрстка окон, VFX, соответствие макетам — собирать в один блок «Проверка графики и визуала фичи». Внутри перечислить области списком, а не заводить по задаче на каждое окно и каждый элемент.

Отдельный блок окно получает только тогда, когда у него **своя механика** (расчёты, состояния, ветвления, взаимодействие с сервером), а не своё оформление.

Порядок блоков в файле — от запуска фичи к её завершению, затем кросс-функциональные, затем платформенные. Ориентир: запуск → лаунчер → ресурсы → основная механика → переходы и завершение → туториалы → UI → данные и сервер → кросс-функциональные → платформы.

## Что попадает в проверки

Проверка — **атомарное проверяемое утверждение**, а не «проверить, что всё работает».

Источники проверок — **только ТЗ и шаблон**:
- каждое явное требование и числовой параметр из ТЗ;
- каждая ветка «если … то …», включая негативную, если она описана;
- каждое «Важно!» и примечание;
- переходы между состояниями объекта, описанные в ТЗ;
- формулы — на примерах из ТЗ, если примеры есть;
- пункты шаблонных блоков, применимые к этой фиче.

**Чего в проверки не писать:**
- требований, которых в ТЗ нет, — не додумывать и не выводить «по смыслу»;
- проверок по разделам, которые в ТЗ не описаны, — блок оставить пустым, вопрос задать в ответе;
- найденных пробелов, противоречий и вопросов — в файле их нет.

**Не усложнять.** Одна проверка на осмысленное требование, а не на каждый элемент интерфейса и каждую подпись. Формулировка ровно такая, как в ТЗ: `Событие доступно после прохождения 26 уровня (настраиваемый параметр)` — да; развёрнутый сценарий с шагами — нет.

### Аналитика, нотификации, тексты — перечни не придумывать

Состав аналитики описывает аналитик, состав текстов и пушей — их владельцы. Сочинённый список всё равно пойдёт в переписывание.

- Есть явная ссылка на таблицу или задачу — приложить её к блоку, и всё.
- Ссылки нет либо она неявная («Заполняется аналитиком», ссылка на общий документ без раздела по фиче) — **оставить блок пустым** и сказать об этом в ответе на ревью, а не заполнять блок догадками.
