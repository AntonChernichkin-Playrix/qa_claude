# Декомпозиция ТЗ на QA-задачи

Превращает ТЗ фичи в набор задач-проверок: сначала в markdown-файл на ревью, затем — подзадачами в Asana через MCP.

**Главный принцип: ничего не создавать в Asana, пока файл не согласован.** Asana — последний шаг, только после явного «ок» и полученной ссылки.

## Порядок работы

Пять шагов строго последовательно. Не перескакивать вперёд и не совмещать.

### Шаг 1. Найти ТЗ

1. Если путь не назван — искать `*.md` в `docs/`, корне проекта, затем `~/Downloads` и `~/Desktop`. Отсортировать по времени изменения, показать кандидатов, подтвердить выбор.
2. Основной формат — `.md`. Если пришёл PDF, извлечь текст:
   ```bash
   uv venv /tmp/pdfenv -q && uv pip install --python /tmp/pdfenv/bin/python pypdf -q
   /tmp/pdfenv/bin/python -c "
   from pypdf import PdfReader
   r=PdfReader('<путь>')
   open('/tmp/tz.txt','w').write(''.join('\n===== PAGE %d =====\n'%i+(p.extract_text() or '') for i,p in enumerate(r.pages,1)))"
   ```
   В извлечённом тексте маркеры списков (`•`, `◦`, `1.`) уезжают в конец страницы отдельными строками — ориентироваться на смысл, а не на отступы. Таблицы баланса разваливаются: не пытаться восстановить числа, ставить `[ГД]`.
3. **Прочитать ТЗ целиком.** Не по диагонали: половина проверок рождается из фраз «Важно!», «Например», «может меняться», сносок и примечаний.
4. Зафиксировать точное название документа — оно пойдёт в строку `Источник:` каждой задачи.
5. Выписать оглавление ТЗ — список разделов и подразделов. Это скелет декомпозиции и чек-лист покрытия.

### Шаг 2. Собрать декомпозицию в файл

Создать `docs/decomposition-<slug>.md` (slug — короткое имя фичи, например `idl-remaster`).

Порядок сборки:

1. **Взять обязательные разделы** из [reference/template-blocks.md](reference/template-blocks.md) — это каркас. 38 блоков шаблона «(ХХХ) Шаблон. Декомпозиция фичи со стороны QA»: планирование, запуск и инфраструктура, данные и сервер, кросс-функциональные, платформы, просмотры и стабилизация. Заголовки у всех фич одинаковые, **описания проверок — свои**: каждый блок наполнить конкретикой из ТЗ, а не скопировать.
2. **Пройти по разделам ТЗ сверху вниз** и добавить функциональные блоки — механика фичи, её объекты, флоу, окна. Они вставляются в середину, между блоком про завершение и кросс-функциональными. Правила укрупнения и дробления — в разделе «Как резать ТЗ на блоки» ниже.
3. **Наполнить каждый блок проверками** по формату из [reference/format.md](reference/format.md).
4. **Отметить пробелы** маркером `[GAP-xx]` со сквозной нумерацией. Не выдумывать требование, которого нет в ТЗ.
5. **Собрать вопросы по неприменимым обязательным блокам** — см. следующий раздел. Это делается до ревью.
6. Свести статистику: сколько блоков, какие разделы ТЗ куда легли, какие разделы не покрыты и почему, список всех GAP.

### Шаг 2а. Уточнить неприменимые обязательные блоки

Если анализ ТЗ показывает, что обязательного раздела в этой фиче быть не может — нет туториалов, нет покупок, событие не серверное — **не удалять блок молча и не тащить его пустым**. Собрать все такие случаи и задать вопрос одним списком, до отдачи файла на ревью.

Ключевое различие, которое нужно проговорить в вопросе:

| Ситуация | Что делать |
|---|---|
| Функциональности в фиче нет по существу (клиентское событие → Prod-сервер) | Предложить убрать, дождаться подтверждения |
| Раздела нет в ТЗ, но функциональность вероятна (пуши, тексты, звуки) | Это `[GAP-xx]`: блок оставить, требования запросить |

**Про версию не спрашивать.** Номер версии в названиях задач не пишется и в вопросы не выносится — его проставляет QA сам. Если в ТЗ есть пометка, что часть функциональности отложена на будущее, фиксировать её как `[GAP-xx]` про объём релиза, не превращая в вопрос о целевой версии.

Формат вопроса и примеры — в конце [reference/template-blocks.md](reference/template-blocks.md).

Файл содержит **только текст будущих задач** — то, что уедет в Asana. Никаких рассуждений о процессе внутри блоков.

### Шаг 3. Попросить ревью

Показать в ответе:
- путь к файлу и число блоков;
- таблицу покрытия: раздел ТЗ → номер блока (и явно — что не покрыто);
- полный список `[GAP-xx]` — это главное, ради чего читают декомпозицию;
- вопросы из шага 2а по неприменимым обязательным блокам;
- спорные решения: что объединил, что разбил, какие обязательные блоки предлагаешь убрать.

Затем прямо попросить ревью и **остановиться**. Не начинать создавать задачи и не предлагать это делать до правок.

### Шаг 4. Внести правки

Править файл по замечаниям. После правок — короткая сводка: что изменилось, какие GAP закрыты. Снова ждать подтверждения. Цикл повторять, пока не скажут, что всё устраивает.

### Шаг 5. Создать подзадачи в Asana

1. Попросить **ссылку на родительскую задачу** в Asana. Не искать её самому и не угадывать проект.
2. Из ссылки вида `https://app.asana.com/1/<workspace>/project/<project_gid>/task/<task_gid>` взять последний `<task_gid>`. В старом формате `/0/<project>/<task>` — тоже последний сегмент.
3. Проверить задачу перед записью: `asana_get_task` — показать название, проект, текущее число подзадач. Подтвердить, что цель верная.
4. Создать подзадачи **по порядку** через `asana_create_subtask` (`parent`, `name`, `notes`). Asana хранит порядок добавления, поэтому создавать строго сверху вниз по файлу.
5. Блоки, помеченные в файле строкой `Вложенная подзадача: Написание чек-листа`, а также платформы внутри блока «Проверка фичи на разных платформах» — создавать вторым проходом, с `parent` = gid только что созданного блока.
6. Ничего не назначать и не проставлять дедлайны, если об этом не просили.
6. По завершении — отчёт: сколько создано, ссылка на родителя, список неудавшихся (если были) с причиной.

Если MCP-сервер Asana недоступен, не переходить на прямые curl-запросы молча — сказать об этом и предложить вариант.

## Как резать ТЗ на блоки

Один блок = одна область, которую тестировщик может взять и проверить целиком за один заход.

**Ориентир по размеру:** 3–15 проверок. Меньше трёх — скорее всего, кусок соседнего блока. Больше пятнадцати — блок пора делить.

Дробить, когда:
- у сценариев **разные условия входа**. Пример: «Логика завершения» в ТЗ — один раздел, но в декомпозиции это три задачи: завершение по прогрессу, 13-й бонусный рудник, завершение по таймеру. Разные триггеры, разные состояния игрока, разные награды.
- внутри раздела есть **самостоятельная подсистема со своим UI**. Пример: из «Персонажи крабы» выделены отдельно «механика крабов» (перемещение, спавн, мерж, грейды) и «система подсказок и хелперов мержа» (подсветки, покачивания, VFX простоя).
- у объекта **отдельное сложное окно**. Пример: «Окно дороги наград» — своя задача, хотя остальные окна собраны в одну.

Объединять, когда:
- разделы **однотипные и проверяются одним прогоном**. Пример: стартовое окно, банк бочек, инфо-окно, окна завершения → одна задача «Проверка UI-окон». Список окон при этом перечислить внутри.
- раздел ТЗ **пустой или чисто справочный** («Графика», «Полезные ссылки») — влить в соседние блоки или в кросс-функциональные.

Порядок блоков в файле — от запуска фичи к её завершению, затем кросс-функциональные, затем платформенные. Ориентир: запуск → лаунчер → ресурсы → основная механика → объекты локации → переходы и завершение → туториалы → UI → данные и сервер → кросс-функциональные → платформы.

## Что попадает в проверки

Проверка — **атомарное проверяемое утверждение**, а не «проверить, что всё работает».

Источники проверок внутри раздела ТЗ:
- каждое явное требование и числовой параметр;
- каждая ветка «если … то …», включая негативную;
- каждое «Важно!» и примечание — это места, где разработка ошибается чаще всего;
- переходы между состояниями объекта (разрушен → восстановлен → запущен → максимальный уровень);
- формулы — проверять на примерах из ТЗ, если они есть.

Что добавлять **сверх ТЗ**, из QA-опыта (в примере-эталоне так и сделано):
- проверки на старых сохранках и на игроках из предыдущих версий фичи;
- поведение при прерываниях: сворачивание, потеря сети, синхронизация посреди флоу;
- специфика фичи в шаблонных блоках — например, в блоке про low-устройства отдельно отметить стресс-сценарий «много крабов + ускоритель x10 + VFX».

Конкретика важнее полноты формулировок: `Событие доступно после прохождения 26 уровня (настраиваемый параметр)` лучше, чем `Проверить условие по уровню`.

## Работа с пробелами в ТЗ

ТЗ всегда неполное. Найденные дыры — ценный результат декомпозиции, их нельзя молча закрывать домыслами.

- `[GAP-xx: описание]` — пробел, противоречие или отсутствующая ссылка. Нумерация сквозная по всему файлу.
- `[ГД]` — значение берётся из таблицы баланса, в ТЗ его нет.
- Если механика упомянута, но не описана — завести блок и написать прямо, что он заблокирован до получения раздела ТЗ. Пример из эталона:
  > `[GAP-13]` Механика Perfect Progress отсутствует в ТЗ. Требования перечислить после получения от ГД раздела ТЗ или ссылки на документ механики. До этого задача заблокирована.
- Пометки статуса (`✅`, `⛔️`, `❓`) в тексте проверок допустимы, если ревьюер ими пользуется, но по умолчанию не ставить.
